# Spec 迭代：从坏 Spec 到好 Spec

## 为什么 Spec 会"坏"

写给 AI Agent 的 Spec 经常出问题：

- **模糊动词**："优化一下性能" → Agent 不知道"优化"的标准是什么
- **缺边界条件**："处理用户输入" → 没说空输入、超长输入、特殊字符怎么办
- **缺验收标准**："加一个搜索功能" → 什么算"搜索成功"？部分匹配算吗？
- **范围蔓延**：一句话里塞了三个不相关的需求

## 坏 Spec 的后果

Agent 收到坏 Spec 后的典型行为：

1. **猜测你的意思**：可能猜对，也可能南辕北辙
2. **过度实现**：你说"加个按钮"，它顺手重构了半个页面
3. **遗漏关键逻辑**：你没提边界，它就不处理边界
4. **无法验收**：做完了你也不知道对不对，因为"对"没定义

## 修正 Spec 的核心手法

| 问题 | 修正方法 |
|------|----------|
| 动词模糊 | 换成可量化描述："响应时间 < 200ms" |
| 缺边界 | 列出至少 3 个边界场景 |
| 缺验收标准 | 写出"做完后如何验证成功"的步骤 |
| 范围蔓延 | 拆成多个独立 Spec，每个只做一件事 |

## 迭代循环

```
写 Spec → 让 Agent 执行 → 看产出 → 发现问题 → 修正 Spec → 再执行
```

关键原则：
- 第一版 Spec 几乎一定有问题，这是正常的
- 修正时要**诊断是 Spec 的问题还是 Agent 的问题**
- 好的修正是让下一次执行更可预测，而不是加更多文字
