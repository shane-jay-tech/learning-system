# 多轮迭代：真实项目中的连续决策

## 真实项目不是一次交付

在真实开发中，你和 Agent 的协作不是"写一次 Spec → 收一次代码"就结束。实际情况是：

1. **需求会变**：产品经理中途加了新要求
2. **测试会暴露问题**：上线前发现边界 case
3. **依赖会更新**：第三方 API 改了接口
4. **用户会反馈**：上线后发现体验问题

## 多轮迭代的核心能力

| 能力 | 具体表现 |
|------|----------|
| 变更管理 | 新需求来了，判断是改现有代码还是新开分支 |
| 回归防护 | 改一处不破坏其他已完成功能 |
| 范围控制 | 拒绝不合理的需求蔓延 |
| 优先级排序 | 多个问题同时出现时，先修哪个 |
| 增量交付 | 不推翻重来，在现有基础上迭代 |

## 给 Agent 的迭代指令原则

1. **指明上下文**："基于上一轮的代码，修改 X 函数的 Y 行为"
2. **保护已完成**："不要改动 A 模块和 B 接口"
3. **说明优先级**："先修 bug，再加新功能"
4. **提供测试基线**："修改后确保现有测试仍然通过"
5. **控制粒度**：每轮只做一件事，做完验收再做下一件

## 常见陷阱

- **全部重写冲动**：Agent 经常建议"这个架构不太好，我重写一遍"——大多数时候应该拒绝
- **连锁修改失控**：改了 A 导致 B 坏了，修 B 又导致 C 坏了——说明改动粒度太大
- **遗忘上文**：Agent 上下文窗口有限，关键约束需要每轮重复
