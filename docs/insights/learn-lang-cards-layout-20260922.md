## 二、机制澄清：Streamlit 的 `st.columns` **不会折行**，4+1 是取模造出来的

任务书把症状描述成「第 5 张卡独占次行左 1/4」——**视觉描述正确，但成因不是折行**。原码 12 行：

```python
    n = len(ALL_LANGS)
    cols = st.columns(min(n, 4))          # 只开了 4 个列容器
    for i, lang in enumerate(ALL_LANGS):  # 5 次迭代
        ...
        with cols[i % len(cols)]:         # 第 5 次 i=4 → cols[0]，回到第 1 列内部
```

`st.columns(4)` 一次调用 ＝ **一个 flex 容器 ＋ 4 个列**，容器内不再有第 5 个位置。`i % len(cols)` 于是把第 5 张卡**追加进第 1 列的纵向堆叠**：卡宽仍是 1/4 行宽、右边 3/4 空着——与"折行"殊途同归，但**改法完全不同**（要断行必须自己分块、自己再调 `st.columns`，不能指望 CSS 折）。

安装包侧取证（`streamlit/elements/layouts.py:574-620`，1.58.0）：

```
        weights = spec
        if isinstance(weights, int):
            weights = (1,) * weights
        if len(weights) == 0 or any(weight <= 0 for weight in weights):
            raise StreamlitInvalidColumnSpecError()      # ⇒ 0 权重会被拒，末行补位不能用 0
        ...
        block_proto.flex_container.direction = BlockProto.FlexContainer.Direction.HORIZONTAL
        block_proto.flex_container.wrap = True
```

三条从源码直读的结论，全部影响到本单选型：
1. **槽位数由调用方决定**，一次调用只产一行 ⇒ 多行必须多次调用（本仓成就墙 `_render_achievements` 里 `for i in range(0, len(all_states), cols_per_row): cols = st.columns(cols_per_row)` 就是这个分块房式写法，语言节此前是全仓唯一的取模异类）。
2. **`spec` 可以是 int 或数列，且权重必须是正数**（`weight <= 0` 直接抛 `StreamlitInvalidColumnSpecError`）⇒ 想给末行补"空槽"居中，不能用 `0`，只能用 `(3-count)/2` 这种正小数。
3. `flex_container.wrap = True` 确实写进了 proto ⇒ 前端 flex 容器**理论上是可 wrap 的**。但列宽实现（压缩产物里 `stColumn` 的 styled 定义）本次**没能静态读出来**（多次 grep `flex:`／`minWidth:` 组合式片段未命中目标块），所以「各列百分比 ＋ gap 是否会在 ≤1280（本仓 `ui/styles.py:292-295` 显式加了 `flex-wrap: wrap`）溢出换行」**属待浏览器实测项**，见第五节假设点 A-3。

## 三、选型：三条候选的取舍（关键——「5 列等宽」是被历史否掉过的）

| 方案 | 每行列数 | 卡宽（1366 推演） | 次行留白 | 判定 |
|---|---|---|---|---|
| **5 列等宽** `st.columns(n)` | 5 | ≈**183px** | 无 | **否决** |
| 3+2（末行左对齐） | 3 | ≈333px | 右 1/3 空 | 可行但仍是断裂 |
| **3+2（末行居中补空槽）** ← 本单采用 | 3 | ≈333px | 左右各 ≈166px 对称 | **采用** |
| 首卡跨列（`[2,1,1]`＋`[1,1]`） | 3~4 | 首卡 ≈665px，其余 ≈333px | — | **否决** |

**为什么不能选最直觉的「5 列等宽」**——它正是本仓**已经改掉**的东西，有三处书面与机械证据：

- `docs/insights/learning-ergonomics-scan-20260911.md:21`：「`dashboard.py:85` `st.columns(min(n, 5))`——**1366 断点挤压**：5 列在侧栏展开的内容区（~1100px）每列仅 ~210px，卡片文字换行挤压」，期望值写的是「≥5 列时降为 **3-4 列**或提前 wrap」。
- `docs/insights/learning-ergo-fix-20260912.md:21`：修复②「`st.columns(min(n, 5))` → `min(n, 4)`」，配套加 `@media (max-width: 1280px)`。
- 落地 commit `a56be3d`（`git log -S "min(n, 5)"` 唯一命中），并把该决定钉成了源级断言 `tests/test_ergo_h912_13.py::test_dashboard_column_cap_and_1280_breakpoint`（原断言含 `"min(n, 5)" not in src`）。

⇒ 5 等宽会把每列从 ≈246px 进一步压到 ≈183px，比当年被判「挤压」的 210px **更窄**，属直接回退一次已验收的人体工学修复。
「首卡跨列」否决理由：首卡 ≈665px 与其余 ≈333px 差一倍，`st.metric` 标签在超宽卡里被拉散，且它对 6/7 门语言没有可延展性——不解决"均衡"，只是把断裂换了个方向。
「3+2 左对齐」改善不足：留白从右 3/4 缩到右 1/3，仍是单侧断裂。

**选 3 而不是 4 作每行上限**：5 在每行 4 下必然是 4+1（取模或换行都一样残缺）；每行 3 恰好 3+2，且卡宽回到 1/3 行宽（比现状更宽松），同时**仍 ≤4 列**，h912-13 的上限意图不破。n 将来变 6→3+3、7→3+3+1（末张居中），无需再改码。

## 五、断言语义调整（为什么动 test_ergo_h912_13 且仍是 4 passed）

原断言 `"st.columns(min(n, 4))" in src` 钉的是**一个具体写法**，本节一换写法它必红——这正是任务书预告的「列上限断言语义（若涉及）」。**文件内测试函数数量保持 4 个不变**，只改这 1 个函数的实现与 docstring，三条等价把守替它：

- a) `"min(n, 5)" not in src` 原样保留（原意图的正面表述）；
- b) 机械扫描 `dashboard.py` 所有**字面量入参**的 `st.columns` 调用，逐个断言槽位数 ≤4（`st.columns(spec)` 这类变量入参静态扫不到，交给 c 兜）；
- c) 直接跑纯函数 `_lang_card_rows`：断言 5 门语言排 3+2、满行不补位、末行权重恰为 `[0.5, 1, 1, 0.5]` 且首槽为 1、每行权重和＝3、空表不产行。

另加防回归：取模叠卡 `i % len(cols)` 不得再出现在**代码行**里。这条的"只扫代码行"不是妥协——实施时写在 `dashboard.py:139` 的解释性注释原文引用了那个旧写法，**第一次实跑就被自己的守卫打红**（原样读数：

```

E       AssertionError: 取模叠卡会把末行卡片塞回首列，造成 4+1 断裂
```

），据此改成剥整行注释后再扫。**该次意外失败同时反证了这条守卫是活的**。
