# 回填去重双键化（l927-13）执行记录

## 〇、一句话

`scripts/backfill_events.py` 过去**只**拿 payload 里的 `attempt_id` 当去重键，而库里两类合法事件行的 payload 根本没有这个字段
（2026-07 年代的回填产物 ＋ `core/judge.py:203-206` 至今的实时 `emit_event`），于是这类行**永远判不出重复**、
任何人重跑一次 `--apply` 就把既有 attempts 整批再复制一遍事件（2026-09-25 生产库 `learning_events` 51→81 行即此）。
本次把它改成**精确键命中优先、老行按「计数额度」兜底**的双层判定，并在 `backfill()` 上加了可选 `db_path` 注库参数。

## 一、缺陷的磁盘形态（154239 §D 原文复核）

§D 给的证据是在**生产库**上点出来的两代行（在册、按用户裁决「两说都留」，本单一行未删改）：

| 世代 | `created_at` | `attempt_submitted` 的 payload | `problem_passed` 的 payload |
|---|---|---|---|
| 老代（历史回填） | 2026-07-05 05:23:57 | `{"passed": true}` ← **无 attempt_id** | `None` |
| 新代（09-25 事故重跑） | 2026-09-25 12:49:09 | `{"passed": true, "attempt_id": 1}` | `{"attempt_id": 1}` |

事故回填日志自报 `duplicate_skipped = 0`——不是"没重复"，是**一笔都没判出来**。

## 二、修复口径（与 §D／遗留问题 #2 的建议**不同**，差异是有意的）

154239「遗留问题」#2 的建议原文是「把键从 payload `attempt_id` **退化**为 `(event_type, lang, problem_id, local_date)` 复合键」。
照字面做会引入第二个缺陷：同题同天的多次提交在事件表里本就是**多行**（`attempts` 有 3 条同日同题记录 ⇒ 老代回填写了 6 行），
按日期判重会把它们吞成 1 行——那正是被替换掉的旧注释"此前按日期去重会丢记录"所防护的东西。

落地口径改成两层，命中顺序即优先级：

1. **精确键** `(event_type, lang, problem_id, attempt_id)` —— 只对 payload 读得出 `attempt_id` 的行生效；命中即跳过，**不消费额度**。
2. **退化额度** `(event_type, lang, problem_id, local_date)` —— payload 为 NULL、无该字段、或 JSON 坏到解析不出来的行，
   每条各发一条"已被代表"额度；候选事件命中时**消费一条**，额度用完后该 key 下的后续提交照常补插（补插行带 `attempt_id`，下轮走精确键）。

为什么额度是稳的：额度每轮**从当前库重算**、老行不会被删除，而精确键优先于额度消费 ⇒ 混合世代（事故后的 60 行状态）
下老行即使"配错对象"也不会引发新一轮复制。实测见 §四 的 `mixed_vintages`。

坏 JSON（`'{"passed": true'`）归入老行一支——旧实现把它当"读不出 aid 就整个忽略"，重跑会复制这一行。

## 三、顺带补的安全面（154239 遗留问题 #2 的后半句）
