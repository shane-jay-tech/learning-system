- 写序与 dashboard 侧**相反且更良**：path 是 `emit → set_meta`，失败时 meta 未落 ⇒ 下一帧重试，
  不产生 dashboard 那种「本地有账、事件库永无、永久丢一条曝光」的 A2 缺陷；
  代价是失败帧里「已完成里程碑」的提示会随整页一起消失。

  `grep -n "raise\|RuntimeError\|事件库写入失败" tests/test_path_event_dedup.py` **零命中**
  ⇒ 这两枚 emit 的失败路径**零行为桩**。

### 两案

**甲：补 per-item except，与 dashboard 口径拉齐（推荐）**

- 最小改动面：`ui/pages/path.py` 单文件，约 +10 行——
  ① 头部 `import logging` ＋ `logger = logging.getLogger(__name__)`（该文件现**零 logger**，
  `grep -n "logger" ui/pages/path.py` 无命中，这是甲案唯一的新增依赖）；
  ② `:207` 与 `:216` 各包一层 `try/except Exception: logger.debug("path: … 事件上报失败", exc_info=True)`；
  ③ 同批在 `tests/test_path_event_dedup.py` 或新档补 2 例失败注入桩（照
  `test_dashboard_event_failures.py` 的 `_Emitter` 模式：抛错后断言里程碑仍全渲、meta 未落、恰 1 条 DEBUG 带栈）。
- 行为变化：事件写失败从「整页红 traceback」变「静默降级＋DEBUG 日志」，与 l923-07/l924-01 已确立的
  「面板不因上报失败而炸」同向；写序未动 ⇒ 不吞 A2 裁决面。
- 回滚成本：单文件 revert＋2 例删除，无数据面、无迁移。
- 风险：新 logger 名 `ui.pages.path` 需与既有 `test_ergo_h912_13.py` 的 dashboard 专项扫描共存
  （该扫描只读 `dashboard.py`，不受扰）。
- 🔴 属生产码（UI 层）改动 ⇒ **本波只读位不落**，形状交回主班派写位班次。

**乙：维持裸 emit＋只出文档**

- 口径＝「path_started / milestone_completed 是进度权威源，写不进去就该让用户看见红」。
- 站不太住的地方：这两枚事件**不是**权威源——里程碑完成判定走 `dao.milestone_progress()` 实时算，
  `path_started` 去重靠 `meta` 表；事件库只是漏斗统计（`core/progress.py` 的 events 面）。
  红 traceback 换来的是「整页不可读」，而不是「数据可信」。
- 成本：零码改动，但把 l922-103 已经裁过的口径在第二个文件上破一次例，后续每新增一枚 emit 都要重裁。

**推荐＝甲**，理由：本仓已在 dashboard 侧把「上报失败不得吞掉渲染」钉成规格并有对照例
（`test_both_surfaces_share_the_same_per_item_containment_shape`，`tests/test_dashboard_event_failures.py:734`），
`path.py` 是仅剩的裸 emit 面；对它做例外会让第七节那条「两区形态一致」的断言只覆盖半个 UI。
