## 二、三例各钉哪一格

1. `test_first_export_miss_serializes_once_and_writes_cache_into_session_state`（**未命中／首次导出**）
   - `export_json` 恰 1 次；`_export_cache_json` 落 session_state 且逐字等于这次序列化的返回值；
   - `_export_cache_key` 等于**本件独立重算**的六表指纹（照 `dashboard.py:330-335` 的取数方式自己 `COUNT`，
     不调生产码的 `_exp_key`，避免"拿被测对象自证"）；
   - 键组件数 == `export_all(dao)["data"]` 的表数（**绑实取、不写字面量 6**：导出面加第 7 张表而键没跟即红）；
   - `download_button` 的 `data` == 缓存（三者同源：session_state／spy 结果／按钮实参）。
2. `test_second_export_with_unchanged_data_hits_cache_and_recomputes_nothing`（**命中／数据未变**）
   - 连续三次渲染 `exports` 仍 1、键与缓存串都不变；
   - **哨兵探针**：把 `session_state["_export_cache_json"]` 改成非 JSON 哨兵串后再渲染 ⇒
     按钮 `data` 必须恰为哨兵、`exports` 不得新增、哨兵不得被回写覆盖。
     ⇒ 「缓存被拆、每帧重导」的糊法在这里当场红（既件也能抓这一种，见第四节对照）；
     **而「次数不涨但 `data` 换了来源」只有这里能抓**（第四节变异④：既件例 2 全绿、本件红）。
3. `test_key_change_after_real_write_replaces_sentinel_cache`（**未命中回来／判别自检**）
   - 先造命中态并确认吃到哨兵，再真写入一道题 ⇒ 键跟着变、`exports` 变 2、
     哨兵被真串**整体替换**、按钮 `data` 是新串且导出含 2 条 attempts。
   - 本例存在的理由：例 2 的哨兵断言若无例 3 兜底，可以靠「未命中分支根本不替换缓存」而**永绿**。
   - ⇒ 卷宗点名的「两用例」＝例 1／例 2；例 3 是让这两条有牙的自检，不额外扩判据面。
